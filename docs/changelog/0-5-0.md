# 0.5.0

Released 2026-11-10. In this release `src/` and the shared test helpers match WordPress core trunk
as of [r65378](https://core.trac.wordpress.org/changeset/65378), byte for byte.

## Ported from core

| Changeset | Change | Props |
|---|---|---|
| [r65272](https://core.trac.wordpress.org/changeset/65272) | The tests follow core's PHPUnit guidelines: a summary, `@covers` and a message for each assertion. The docblocks no longer refer to the feature plugin. | peterwilsoncc |
| [r65373](https://core.trac.wordpress.org/changeset/65373) | A failed read of the root key no longer replaces it, which made every stored secret unreadable. Only a write creates a root key. [#66413](https://core.trac.wordpress.org/ticket/66413) | aryanjasala, dhrupo, ericmann |
| [r65375](https://core.trac.wordpress.org/changeset/65375) | A secret name can't end in a newline. Secret values and key material are marked `#[\SensitiveParameter]`, so they stay out of stack traces. [#66414](https://core.trac.wordpress.org/ticket/66414) | dhrupo, aryanjasala, ericmann |
| [r65377](https://core.trac.wordpress.org/changeset/65377) | Summaries, `@covers` and messages for r65375's tests. | – |
| [r65378](https://core.trac.wordpress.org/changeset/65378) | The `secrets.php` drop-in can set its overrides as plain variables, such as `$wp_secrets_keyring = new My_Keyring();`. The plugin's own drop-in loader does the same. | ericmann, jorbin |

peterwilsoncc committed r65272, and whyisjake committed r65373 through r65378.

Two changes in those changesets are not in the plugin, because they edit core admin files the plugin
can't change. WordPress 7.2 has both:

- [r65374](https://core.trac.wordpress.org/changeset/65374) lists `secrets.php` under Plugins >
  Drop-ins and in Site Health Info. Props nofearinc, ericmann.
- r65375 masks `_wp_secrets_root_key` on Settings > All Settings, where saving it changed made
  every stored secret unreadable. Don't edit that field on WordPress 7.1 or earlier.

## Changed

- **Drop-ins should mark their own sensitive parameters.** Attributes aren't inherited, so a
  keyring's `wrap()` and a provider's `set()` add `#[\SensitiveParameter]` themselves. The examples
  and [`drop-in-example.php`](../reference/drop-in-example.php) now do. On PHP 7.4 the attribute
  line is a comment.
- **[ADR 0017](../decisions/0017-abstract-classes-for-the-extension-points.md):** the provider,
  store and keyring become abstract classes instead of interfaces, so a later release can add a
  method without breaking every drop-in. The plugin ports it once core commits
  [PR 15744](https://github.com/WordPress/wordpress-develop/pull/15744).

## Coming in core: `WP_SECRETS_KEY` becomes required

As in 0.4.0, this release still derives the key from `LOGGED_IN_KEY` and `LOGGED_IN_SALT` when
`WP_SECRETS_KEY` is not defined. [PR 15258](https://github.com/WordPress/wordpress-develop/pull/15258)
removes that fallback in core ([ADR 0016](../decisions/0016-require-wp-secrets-key.md)), and has
been tested and reviewed. It also adds `wp_is_secrets_api_available()`, which returns false while
there is no usable key, or while the key can't unlock the stored secrets.

Define `WP_SECRETS_KEY` now. On a site that already stores secrets under the fallback, move them
first, or they become unreadable. The steps from 0.4.0 still apply:

1. Set `WP_SECRETS_KEY` to a new value, from `wp secret generate-key`.
2. Set `WP_SECRETS_KEY_PREVIOUS` to the old `LOGGED_IN_KEY . LOGGED_IN_SALT`, the two values
   joined together.
3. Run `wp secret rotate`.
4. Remove `WP_SECRETS_KEY_PREVIOUS`.
