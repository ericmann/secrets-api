# 0.4.0

Released 2026-10-30. The Secrets API landed in WordPress core trunk for 7.2 as
[r64337](https://core.trac.wordpress.org/changeset/64337) ([#66187](https://core.trac.wordpress.org/ticket/66187)).
Since then the sync runs the other way: core trunk is the source, and the plugin ports each core
changeset into `src/`. In this release `src/` and the shared test helpers match trunk as of
[r64995](https://core.trac.wordpress.org/changeset/64995), byte for byte.

## Changed

- **WordPress 6.8 is the minimum.** r64690 uses `array_all()`, which core polyfills only from 6.8.
  CI has a PHP 7.4 / WordPress 6.8 leg.
- **The WP-CLI commands keep working on a WordPress that ships the API.** Core left `wp secret` and
  `wp network-secret` out. On 7.2 the plugin now registers them on core's implementation and loads
  nothing else. `migrate-legacy` exits with an explanation there instead. See
  [ADR 0014](../decisions/0014-the-plugin-keeps-wp-cli-on-a-core-that-ships-the-api.md).
- **The AWS Secrets Manager and Vault examples skip an unchanged write,** so they pass the
  conformance test from r64674.

## Fixed

- On a 7.2 beta, RC or trunk build, the plugin showed the "another plugin has already declared
  `wp_get_secret()`" error instead of standing down, because `version_compare()` ranks
  `7.2-beta1` below `7.2`. Only the release part of the version is compared now.
- The test suite runs against a WordPress that ships the API. Every trunk job had failed on a
  duplicate test helper since r64337.

## Coming in core: `WP_SECRETS_KEY` becomes required

This release, like core trunk today, still derives the key from `LOGGED_IN_KEY` and
`LOGGED_IN_SALT` when `WP_SECRETS_KEY` is not defined. That is about to change. Rotating the salts
locks every secret on such a site ([#66187 comment:24](https://core.trac.wordpress.org/ticket/66187#comment:24)).
The salts were also read without the checks `wp_salt()` applies
([comment:27](https://core.trac.wordpress.org/ticket/66187#comment:27)). The decision is
[ADR 0016](../decisions/0016-require-wp-secrets-key.md), which supersedes
[ADR 0015](../decisions/0015-keep-the-salt-fallback-and-generate-a-key-at-install.md). The plugin
ports the change once core commits it.

Define `WP_SECRETS_KEY` now. On a site that already stores secrets under the fallback, move them
first, or they become unreadable:

1. Set `WP_SECRETS_KEY` to a new value, from `wp secret generate-key`.
2. Set `WP_SECRETS_KEY_PREVIOUS` to the old `LOGGED_IN_KEY . LOGGED_IN_SALT`, the two values
   joined together.
3. Run `wp secret rotate`.
4. Remove `WP_SECRETS_KEY_PREVIOUS`.
