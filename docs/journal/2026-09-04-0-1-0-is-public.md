# 0.1.0 is public

I tagged `v0.1.0` today and the repository is public. This is the feature plugin for the
[Secrets API proposed for WordPress 7.2][proposal], published on make/core on 25 August. The
proposal said the implementation would ship as a plugin first so people could run it rather than
read about it. This is that plugin.

## What shipped

The public surface is the one the proposal describes. `wp_set_secret()`, `wp_get_secret()`,
`wp_delete_secret()`, and `wp_import_option_as_secret()` are there with the proposed signatures.
`wp_get_secret()` returns a `WP_Secret`, `null` when the secret does not exist, or a `WP_Error`
when it exists and could not be read. Those three states never collapse. `WP_Secret` masks itself
in every output path and gives up the plaintext only through `reveal()`.

Encryption is unconditional. Each secret value is encrypted under its own data key with
XChaCha20-Poly1305, the data key is wrapped by a master key derived per scope from a single root
key, and the root key is the only value stored wrapped. Every ciphertext is bound to its purpose,
scope, site, name, and slot, so a record cannot be moved somewhere else and still decrypt. Rotating
the site key re-wraps one value on a single site or a whole network.

There is no filter anywhere in the core-bound code. An architectural test reads the source and
fails the build if one appears.

A `wp-content/secrets.php` drop-in can replace the provider, the store, or the keyring. The
provider is the outermost of the three and is what a platform holding its own credentials
implements. The shipped provider is one implementation of that same interface. A drop-in that
throws or registers the wrong type fails closed: every call returns `WP_Error`, and nothing falls
back to the default.

Network scope is in. Site and network secrets have separate functions, separate capabilities, and
per-blog master keys derived with `sodium_crypto_kdf_derive_from_key()`. `wp secret` and
`wp network-secret` each have eleven subcommands. Site Health reports the key source,
undecryptable records, and secrets flagged for rotation.

The suite is 359 tests, run on PHP 7.4, 8.0, and 8.3 against WordPress latest and trunk, single
site and multisite. The plugin runs on WordPress 6.6 and later, and stands down on its own once it
detects the API in core.

## What is deliberately not in 0.1.0

No settings screen. The proposal defers it to 7.3, and the accessors a screen needs are the part
that is in scope now.

No compatibility shim for code written against the earlier prototype. A read for a name that
exists only in the prototype's format is upgraded in place the first time, and
`wp secret migrate-legacy` does it in bulk. The prototype's rows are never touched.

No automatic sweep of the options table, no timer that retires an old version, no export, and no
per-plugin isolation. Namespacing groups secrets by owner. Any plugin that can run PHP can read
any secret, and the documentation says so wherever namespaces come up.

Site-key rotation is a WP-CLI command, not an API function, because it needs both the old and the
new constant in `wp-config.php` at once.

Two gaps I know about. Nothing in CI exercises the `sodium_compat` fallback, since every
environment the suite runs in has the extension loaded. And the WP-CLI layer is tested by calling
methods directly, which is how three dispatch bugs went unnoticed until I ran the commands by hand.
Both are in the journal.

## What I would like back

In order of how much it would change the code:

1. **Implement `WP_Secrets_Provider` against a real platform and tell me what broke.** The
   interface was shaped by hosts describing what they need. Nobody has built against it yet, and
   the first implementation will turn something up. A key management service is usually a
   keyring, three methods, rather than a provider.
2. **Run the conformance suite** against your implementation and report what it fails to catch, or
   what it demands that a reasonable backend cannot provide.
3. **Answer an open question.** `docs/journal/open-questions.md` holds only what is still open.
4. **Adopt the API in a plugin** and say where it was awkward. Settled is not the same as
   pleasant.

Bugs, awkward edges, and anything about the code go to
[GitHub issues](https://github.com/ericmann/secrets-api/issues). Anything that would change what
the proposal published belongs on the [make/core thread][proposal] as well, since that is where
the design conversation lives. Security issues go through the private advisory form described in
`SECURITY.md`, never a public issue.

## What is next toward 7.2

The proposal's timeline puts a patch on Trac in late September, matching the plugin's surface at
that point, ahead of Beta 1 on 20 to 22 October.

Before that patch: confirm on the thread the names this implementation added beyond the proposal,
`wp_retire_secret_version()`, `wp_list_secrets()`, and the network functions among them. Get one
real provider built. Add a smoke test that shells out to a real `wp` binary. Try a CI leg with the
libsodium extension disabled.

The patch itself is a copy of `src/` into `wordpress-develop`, with the drop-in loading moved into
`wp-settings.php` and the two capabilities granted by core's role setup rather than an activation
hook. Everything under `src/` is already written to that standard, and the tests enforce it. If
the copy needs more than that, something has gone wrong earlier, and I would rather find out here.
